## 对话数量变化时怎样复用说明

完整规则见[同一项目内的任务拆分、并行与归并](WORKFLOW.md#同一项目内的任务拆分并行与归并)。

制作说明时由AI完成四步：确定长期职责与已有入口；把当前任务/负责人放回原状态；生成一份包含启动、保存、拆分/归并规则的完整正文；用一对话多任务、多对话并行、多变少和新对话接续核对是否有歧义。用户只复制最终完整说明，不自己拼字段或叠贴多个角色模板。

| 变化 | 实际更新什么 |
|---|---|
| 一名英雄增至三名英雄 | 在已授权范围内登记三项任务及来源；不因任务增加自动扩大单英雄试点授权 |
| 一个对话改为三个 | 原任务分配到明确负责范围；先保存基线、新对话实际接收，避免双写 |
| 三个对话改为两个/一个 | 转交仍未完的任务并保留原身份，或按事实记完成/暂停；不因关闭聊天丢任务 |
| 一个对话同时处理英雄视觉与页面UI | 保留两类来源、审批和各自下一步，按当前目标安排执行 |
| 只说“继续”却有多个可能任务 | 仅确认任务/英雄/路线名；已明确的旧对话无需重问 |
| 职责、权限或固定入口真正改变 | 更新项目说明和原约定；数量变化本身通常不需要 |

对话的打开、关闭和实际承接不能由仓库文档自动完成。本轮提供可复用流程和说明文本，不预填前端安装、任务重分配、接收成功或实际效果；接收方仍只记录自己实际接收的范围。

## 日常用法

1. 在已配置对应说明的项目内打开新对话；任务及接任指向唯一明确时说“继续”，有多个任务时加英雄名或任务名即可。执行者核GitHub最新HEAD、当前路由和有效负责范围，简短报告断点，然后按已有授权推进；不抢占仍在施工的任务。
2. 需要换对话时说“收束，我会换对话继续”。执行者保存有意义正文、确认、代码版本、未验事项、未发布工作和下一动作，发布并读回；不要求用户携带长启动词。
3. 上轮中断或未给最终回复，同一对话直接说“继续”进入恢复；新对话／新账号按实际生效的身份、停止依据和当前归属接任。先找实际成果及关联分支／PR，再做未完成步骤；任务和归属已明确时不要求长交接或重复授权。有决定性歧义时只问任务名或旧执行状态。
4. 回传已经入库后，主线在自己的实际运行中主动查收，用户无需转贴整段报告。发布、接收、采用分别记；不会在后台自动唤醒其他ChatGPT对话。

## 必须保持的区分

- 页面UI、英雄视觉和世界观/相关文字可共用设计分支和部分文件，但任务及接续指针不同。main同路径是另一历史资产状态；模板将共享规程指向main、设计来源指向独立分支。减少对话时也保留各项来源与确认，不能用一个收束覆盖所有任务或整树覆盖main。
- 当前正文/任务/收束以各线自己的入口定位，不强制迁移全部旧schema。主线保留普通工程责任；新复核输入与已撤回的工程派发分别判断。无新输入不重复工程、测试或APK。
- 仓库旧版配置已发布，主线旧版说明更新有用户确认且已完成一次新对话自然接续；未独立打开设置界面。支线说明由用户明确报告尚未更新，其安装、各自自然接续和长期收益均未验证；不能用主线单次成功或静态文件检查替代。
- 评分原账本冻结、NET暂停、图稿/候选审批、私密来源和其他线未回传成果继续保护。
