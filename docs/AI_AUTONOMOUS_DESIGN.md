# AI 自主设计｜阶段保存、创作来源与复盘

版本：2026-11-14.METHOD-2。当前专项首先解决长任务中真实成果的保存与接续；设计质量、合理强度、试玩和验证继续由具体任务的原规范约束。

本页是[统一工作流程](WORKFLOW.md#对话中断后的恢复)第7项的操作方法和检查样例，不另立权限、任务账本或业务主线。跨系统协作负责方法改进与可复用结论；各系统主线负责本系统内的协调；英雄执行线负责本英雄的决定、工程和回传。原任务、有效认领、授权及事实源优先。

## 1. 进入本专项时

先沿实际任务入口确定工作对象、已有设计和执行归属。第一英雄[司衡](../worklines/hero-pilot/START_HERE.md)与第二英雄[岑缨](../worklines/hero-pilot-02/START_HERE.md)是不同任务，不能因为共用方法就互换分支、重新设计人物或扩大委托。其他自主设计任务也须有自己的明确范围。

每个任务仍要满足四件事：在受托范围自主决定；把设计做成真实可用的产物；让有价值的增量可恢复；按实际证据说明质量与未验项。用户不需要逐项选择实现细节，也不需要定时提醒保存。

当前的关键问题是：设计和“正在实现”的状态已进入仓库，实际代码、图片和日志却仍留在临时工作区。继续添加同义的“记得保存”不足以说明问题已解决。以下以**实际产物与远端读取证据**判断阶段是否保存。

## 2. 在何处保存、保存什么

阶段按任务需要调整，不要求拆成六个聊天，也不要求每次小编辑提交。完成一个可复用增量，或即将进入长测试、长生成、长上传前，先处理已存在的成果；无需等到准确知道上下文还剩多少。

| 阶段 | 最低可恢复产物 | 进入下一段前核什么 |
|---|---|---|
| 设计形成 | 角色与技能正文、受托决定、规则边界、来源版本、待验假设 | 原入口能读回实际设计；“计划做”与“已经实现”分开 |
| 首个核心实现 | 真实源码、必要接入与配置、基线及已有失败/未测说明 | 新增实现确实已保存；只有分支或设计文件不算代码检查点 |
| 可玩接入 | 选择入口、页面与权威逻辑增量、运行条件 | 能定位所有必要文件；试玩证据与环境限制分别保留 |
| 美术与资源 | 已产生的原图/源层、采用版本、运行导出、导出脚本或参数和资源清单 | 原件及导出均可取回；未保存的原图不能由预览图或文件名替代 |
| 验证与迭代 | 本批原始日志、代码/资产身份、环境、修复、通过/失败/未运行及原因 | 先保全代码再长测，测完保存日志与修复；不同版本的结果不拼成全通过 |
| 候选交付 | 实际分支提交、draft PR、必要设计/实现/强度说明、准确回传 | 发布、主线接收、独立QA、真人强度和正式上线分别成立 |

图片生成完成后有执行机会，就先保全原图和采用关系，再进行后续生成、导出或长验证。代码允许以明确的 in_progress、未测试或有已知失败状态保存到获准专属分支；保存不是合并或部署，不能以“还没最终验收”为理由一直只存本地。

## 3. 每次保存的实际动作

1. **核原范围和当前版本。** 读当前任务、授权及所有权，检查本次真实差分与必要依赖。只处理自己获准的路径；共享对象有有效冲突时先按原流程协调。不得用旧树接新父提交。同时核已跟踪修改、未跟踪新增及被忽略但有恢复价值的原始证据；普通Git补丁不包含全部新文件，不能只保存git diff而漏掉新实现、素材或日志。
2. **先保全原产物。** 将已经存在的正文、代码、素材和原日志保存至本任务获准的持久位置，未变对象直接引用。临时路径、心跳、续租、文件清单和“已做”摘要均不能替代原件。无法直传时只采用原授权和平台实际允许的保全方式，不换包装绕过拒绝。
3. **确认真正发布。** Git对象、树或孤立commit创建成功，不等于分支已发布；核目标ref确实包含本次提交及文件。使用当前父树、expected_sha、force=false；并发变化先重读合并。其他产物位置保留实际成功返回的稳定身份，不把预计ID或计算出的哈希当上传成功。
4. **从持久位置读回。** 核本次关键正文与文件身份，以及接续必需依赖是否能定位。只有相应文件真正读回一致，才报告该范围已保存；正文发布、资产上传、代码发布分别记录，部分成功保持部分状态。
5. **更新原检查点并继续。** 在原CURRENT_STATE、SESSION_CLOSEOUT、RETURN或既有检查点中记真实保存范围、原来源版本、验证限制、未保存/未回传内容、最后外部动作及唯一下一步。接收方自行登记真实读取与采用。无需另建同义台账或为普通阶段关闭对话。

保存结果未知时，先查目的地；已成功的补读回和登记，不盲目重放。保存失败时记录最近成功步骤及明确缺口，先处理有丢失风险的依赖部分；不继续堆积同一批未保存成果，独立且已授权的工作仍可推进。

## 4. 最低检查点内容

复用原字段或文字段落即可，不强制另建文件。一个足够使用的检查点应回答：

- **谁在做什么：** 原任务、工作线、负责范围、授权/认领来源；创作模型及重要贡献按第7节在原记录保留。
- **实际保存在哪：** 仓库与分支、已存在的真实提交；或实际持久产物身份、文件路径和必要内容哈希。
- **保存到哪一步：** 本次原件及依赖、仍仅在本地/尚未定位/尚未回传的部分，不能把未知填成“无”。
- **验证了什么：** 对应源码/资产版本、实际命令或检查、条件、结果及原日志；未运行与失败分别保留。
- **下一动作：** 最近外部动作的成功/失败/未知状态、当前阻断、下一项可执行工作。

恢复者能够沿原入口取回这些实际内容，才支持“本范围可接续”。不要求找回不可见内部推演；关键设计理由和已作决定应写成用户可读的简短记录。

## 5. 中断后从哪里继续

按统一流程先核远端分支、PR和产物，不以旧导航、聊天报告或最终回复缺失代替事实。尚未发现远端代码，不等于本地原件已丢；有可访问原工作目录、已生成资源或可信调用凭据时，核身份后先保全。找回的原件直接复用，只有确实缺失部分才最小重建，新运行不能冒充旧测试。

本次岑缨案例已经核到两种不同证据：公开交接目录保存了设计与早期状态，专属工程分支仍为基线；旧本地工程后来找回了真实实现、原图、导出与原始验证日志，并由本轮做了独立恢复包保全。原英雄分支发布、原线回传及主线接收仍是后续动作，不能由“恢复包已保存”代填。

本次有界保全包名为 `cen-ying-recovery-20261114.zip`；具体私有访问身份由本方私有接续记录和给用户的交付保留，不在公开文档复制。原业务入口与现行分支仍是英雄执行的事实源。这个案例证明本次找回与保全的范围，不能证明原执行者已经主动遵守阶段保存，也不能保证未来自动执行。

## 6. 怎样把有效改进复用

阶段保存或形成一段可用成果后，执行者主动调用原阶段复盘：短看本段目标与结果是否相符、哪里重复或靠用户提醒、交接／验证／方法哪里有实际可简化之处。先在原权限及公开范围内保全成果，再做这次短回看；不必等用户指出问题，也不拖成全系统审计。没有高价值新发现就继续，不制造优化事项。

发现实质问题时，沿原任务和现有改进／回传路径处理，优先修漏用的既有机制；有授权且无冲突的必要差分直接推进。涉及其他线的由其执行并自记接收。若回看后改变实际产物，再保存新版本并更新受影响证据。重要改进只保留预期减少的具体负担、下一自然观察点及收窄／撤回条件。

这是执行者在获得执行机会时调用的阶段动作，不是后台定时扫描，也不能在上下文已被强制截断后自动补保存。本次是用户提出问题后的核查；下一真实阶段是否无需提醒就保存、短回看和接续，仍待观察。

从实际任务的问题出发，先查现有机制与归属，再作最小改动、取得实际证据、记录适用边界；确有复用价值时沿[既有跨系统回传](WORKFLOW.md#跨系统共用改进的直接交接)传递来源与版本。接收方先查等价覆盖，只补实际差分并自记回执，不需要用户再搬运整份资料。

本专项接下来的观察点是：下一次有用代码或素材阶段，执行者能否在用户催促和长测试之前完成真实持久保存；下一接续能否直接取回并继续，减少重做和重复提问。若仍漏用，修执行入口与调用；若流程造成无价值负担，缩小适用范围。文件写入、入口可达、执行者采用和自然效果分别验证。

后续创意质量、规则完整性、合理强度和试玩效率的优化，也按真实任务证据逐项处理；本页不预先宣布全套自主设计能力成熟，不新增定时任务或常驻调度。

## 7. 创作来源与模型标签

用户希望尽量由同一个模型完成一名英雄，并观察不同模型在人物、机制和美术方向上的差别。采用**一个主创标记，加实际发生的重要例外贡献**：在任务开始能确认时就记；阶段保存和换对话接续时核实际来源。主创不因后续工程修复、复核或恢复发布而被覆盖。模型确有变化时追加阶段与贡献范围；无法核实时写“同模型连续性未核实”，不猜测已经更换。

直接复用英雄原 DESIGN／既有交付记录，以及原 PROMPTS／ASSET_MANIFEST；不另建英雄账本，不要求逐句、逐文件记录作者。具体写入和采用仍由原英雄线按其当前身份、认领和授权完成。

| 内容 | 最低充分记录 |
|---|---|
| 主创 | 主导人物与机制决定的可见模型标签；标签来源与核对时间。未知保留待核实。 |
| 重要其他贡献 | 后续模型或子代理实际完成的设计、工程、美术指导、复核、恢复等范围；无实质变化就引用上阶段，不重复填表。 |
| 执行环境 | Chat／Work／其他／未知，与模型标签分列；任务角色及授权另按原来源，不由环境名决定。 |
| 美术来源 | 美术方向／提示词的聊天模型，与实际生成工具、可确认的图像后台模型分别记录。工具名不是后台模型名。 |
| 对应成果 | 引用已有任务、设计、代码提交、图片版本／哈希及重要参考链；绑定这一阶段实际保存的版本。 |

可在原记录直接写一小段：

> 创作来源：主创【可见标签或待核实】，依据【来源、日期】；环境【实际可知值】。本版本贡献【人物／机制等范围】；重要其他贡献【仅列实际例外】。美术指导【标签或未知】，生成工具【实际记录】，后台图像模型【已确认值或未知】。成果版本【原提交／资产身份】。

标签保留来源性质：平台／工具实际返回、可见界面观察、用户提供、执行环境声明、原执行者自报、尚未找到或相互冲突。自报不升级成平台证明；用户提供的旧对话选段不等于完整调用记录。推荐表、Git作者、角色名、作品风格及当前恢复者的模型，都不能倒填历史主创。具体推理档位／版本只在确实可知且有用时追加。

当前核查范围内，司衡与岑缨的原交付记录均没有可靠的确切主创模型标签。岑缨原资产记录写有 `built-in image_gen.imagegen`，其美术指导聊天模型及后台图像模型仍未知。本方只保存核查发现并回传；原英雄线的补标、读取和采用需实际发生后由其记录。这也不表示已经修改游戏展示。

其他任务复用同一方法：只在重要结论、实质成果、模型变化或必要复核时，在原阶段记录留下“可见标签与来源—贡献范围—成果版本”。环境、权限、模型与验证结果保持分列。无需给每条聊天加标签，也不修改通用来源对象的严格字段契约。

模型标签用于追溯与定位复核范围，不能单凭名称自动判作品不可靠或已经通过。实际错误、证据缺口、能力限制、来源冲突和后果决定复核强度；先核受影响结论及产物，再按发现决定是否扩大。换模型或多代理复述同源材料不自动成为独立QA；模型未知本身也不阻断已有可靠产物的恢复。

比较英雄时以“英雄＋版本”为单位，复用原任务要求、规则基线、参考图／提示词、生成工具及重要修改记录。机制可比较特色、决策空间、反制、复杂度和实际强度证据；美术可比较造型、轮廓、色彩与材质。先报告作品差异，再讨论模型可能的影响；同世界约束、前作影响、定向差异化指令、图片生成后台、迭代与人工选择都会影响结果。少数不同英雄不能证明某模型的稳定风格或总体优劣。
