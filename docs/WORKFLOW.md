# GitHub连接器增量工作流程

## 项目内新对话接续与收束

项目说明固定稳定的职责范围、可用路线、仓库、分支和入口；不把当前英雄名单、任务数量或对话数量写成永久限制。当前任务、负责人、批准、下一步保存在既有工作线来源中；同一职责范围可以由一个或多个对话执行，同一对话也可以承接多项明确任务。项目内的新对话与旧对话均适用以下规则。一次配置说明不等于前端已安装、GitHub访问已具备或新对话已实测成功。可复制配置见[项目安排](COORDINATION_SETUP.md)。

**说“继续”时：**

1. 先定位职责和任务。已有对话沿用已明确的工作线及任务；新对话从实际生效的项目说明和当前路由定位。只有任务指向唯一明确、且符合原接任/认领条件时，才凭“继续”接续；唯一固定工作线不保证其中只有一项任务。存在多个可能任务时，仅确认路线、英雄名或任务名；不猜最后活跃线、最近收束、最新修改或默认普通线。唯一任务若仍由另一对话施工，也不因此接管。用户明确换线或调整分工优先于默认入口，但不扩大授权。
2. 核目标分支最新HEAD，固定到该提交读取START_HERE的当前路由、本线当前状态、适用协作正文及授权来源；再沿入口读取本路线相关收束、TASK_FROM_MAIN、RETURN_TO_MAIN和自己的READ_RECEIPTS。各线现有文件名/字段不同，按入口定位，不强制新建同名文件或统一schema。先确认哪些旧断点已被新确认、回传或任务覆盖，再决定下一动作；不能仅按文件名日期或一个历史session_closure恢复旧任务。
3. 查有无与当前任务相关的新输入。主线在实际运行时按现有回传和自己的接收记录主动接收；支线核主线新任务/意见并保护尚未回传成果。没有新差分不重复已完成验证、工程、APK或空轮询。给用户简短说明恢复到哪里、下一有意义动作或真实等待项，并在授权内执行。
4. 先查既有授权、有效暂停和归属。主线仍须有指向本对话的明确用户任命：用户实际采用的项目说明可以明确任命该项目内、满足正常收束或下节中断恢复条件的接续对话；仓库模板、历史别的对话任命、读到主线入口都不自行授予角色。未关闭主线仍在施工或存在身份冲突时，先保护成果和核清接任/并行关系，不能抢占写入。普通线工程转派撤回及其他既有边界不会被“继续”改写。
5. 无法读源时说明具体缺口，完成不依赖缺源的部分，不凭聊天记忆宣称已恢复。GitHub不会自动唤醒其他对话；下一次相应对话被用户唤起时主动查回即可，不把例行转贴报告作为主线接收前提。

### 对话中断后的恢复

“继续／接着做”也触发本节；前次因上下文、额度、工具超时或其他原因中断、没有最终回复或来不及收束时，先恢复实际工作，不要求故障对话另行生成交接。本节落实现行协作正文GITHUB_HANDOFF_WORKFLOW，不新增后台调度或另一套任务账本。

1. **定位原任务和执行范围。** 同一对话沿已经明确的身份、任务及授权继续，核当前所有权，不为中断另建同义任务；原认领仍有效时复用，失效或被接手时按原规程处理。项目内新对话从实际生效的项目说明及当前入口确定任务；跨账号另外核实际连接和工具能力。任务不唯一时只确认任务名／路线，不能凭最近修改时间猜测。
2. **核接任与并发。** 新主线接任需要对本对话生效的用户任命或条件任命。条件可涵盖旧主线正常收束，或有明确依据表明旧执行已中断／停止、尚未收束且不存在同范围有效并发冲突；已有用户停止／转交依据直接使用并注明来源。原系统另有过期认领恢复时，按其既有规程核最后检查点、保留未知未回传成果、取得新有效代次并发布回读；不能只改state字段，也不能把租期到期说成旧后台已经停止。运行图标、没有最终回复、沉默时长、旧active文字或旧历史收束，均不能单独证明当前执行或接任状态。无法隔离同一对象的并发写入时，先做只读恢复，只就尚缺的任务归属／旧执行状态提出一个最小问题；已有停止和接任依据不重问。记录本次中断恢复，不补造旧对话成功收束。
3. **查最后操作的真实结果。** 核相关仓库／目标分支最新HEAD，在固定提交读取入口、当前任务、有效授权、最近检查点和其后差分。上轮写入、提交、建PR、上传或其他外部动作结果未知，先查目标端是否已经成功；已成功则补读回／登记，已生成但未挂接的对象有真实凭据时复用，确认未成功才补必要步骤。聊天“准备保存”不证明没有保存，聊天“已完成”不证明远端已保存；不能因为最终回复缺失而重复执行。
4. **查已保存但未回传的成果。** 沿当前任务的代码仓库、已知分支／PR、父提交、产物位置和验证日志作有限核查。若入口仍指旧版本或未找到上轮成果，在已授权的关联代码仓库有限查找尚未登记的新分支／PR／提交候选，不能只读已登记PR。分支名／时间只作线索，还须核父子关系、实际差分、任务来源和内容；不扫全账户，不接管其他线。状态仍指旧版本、工程已有较新成果时先保护经核实的适用成果，再补本线真实回传／接续导航；较新草稿仍是草稿，不自动变批准或合并。
5. **按实际保存程度续接。** 已保存且已登记，从下一未完成动作继续；已保存未登记，先补登记；可访问的未发布成果，先核来源及并发后保全；只有开工记录且成果无法找回，明确缺口，从最后可证实节点最小重建。原件、代码、原图、导出、原始日志能找回就复用；新重建／新运行另记为新结果，不能冒充丢失原件或旧验证。未知未回传工作保持未知，不填写“无”。
6. **继续必要工作。** 简短说明“找回了什么、断点、下一动作”后，直接推进已有授权内的未完成部分，不停在恢复报告等用户再说一次继续。无具体差分不重跑已通过验证、不重传未变资产、不重新生成已存内容；仅为受影响改动、证据缺口或必要验收补查。授权按原范围继承，连接、网络与运行能力实际核验；环境条件未变化时不重复同一失败调用，也不再次索要已经保存的同范围许可。缺源／能力只阻断依赖部分。
7. **分段保存和读回。** 完成有用阶段、进入长测试／长上传前、已知接近限制或准备换对话时，优先保存真实产物及最低充分恢复信息：任务和负责范围、仓库／分支／真实提交或对象身份、已做／未做／验证条件、未发布和未回传成果、阻断及下一动作。更新原有任务／检查点／回传，按最新HEAD和原并发规程发布读回。无需每小步提交；长调用不给执行机会时不能保证途中保存。发布、接任、前端安装及自然接续效果分别记录。

自主设计任务按[自主设计阶段保存方法](AI_AUTONOMOUS_DESIGN.md)核对每阶段真实产物、持久位置及读回；该方法落实上面的第7项，原任务、认领与回传继续复用。

**能力边界：**本节规定AI再次获得执行机会、收到“继续”时怎样恢复；不保证找回未保存的每个字符或内部推演，不会自动唤醒对话，也不替平台取消旧任务。没有成功收束仍可恢复；取得写入身份仍须满足实际任命和并发条件。

**说“收束／换对话”时：**

- 保存本轮有意义的实际正文、确认来源及范围、代码仓库/分支/提交、验证及未验项。未发布工作须先在原授权目的地保全，记明可恢复位置和未成功事项；不能只留下“已完成”的摘要或把本地临时路径当持久恢复凭据。
- 在本线既有CURRENT_STATE和收束记录中明确：只结束本对话还是有具体任务暂停、当前接续路由、唯一下一动作或等待依赖、未回传成果及并发保护。关闭一次对话不暂停其他线，不关闭整个项目；普通阶段保存也不自动算对话收束。
- 复用本线RETURN_TO_MAIN发布差分。用最新父树、expected_sha和force=false提交，遇并发重读合并；发布后逐项读回，给出实际提交与未完成项。历史收束保留为来源，下一步以本线当前路由为准；不再把长启动词当作用户必须搬运的载体。
- 收束回复以“已保存／尚未保存、接续入口、下一步”收尾。任务和接任指向已唯一明确时，新对话只说“继续”；否则一句路线/英雄/任务名加“继续”即可。一个对话原本负责多项任务时，收束须覆盖其全部未完范围，不因最后讨论其中一项而漏掉其余。只有访问受限、用户另要离线包等实际需要才再提供材料包。

独立UI分支按实际任务区分页面UI、英雄视觉和相关世界观/文字工作，不限定对话数量。现有页面任务沿active_ui_image_task及当前页面基线，英雄视觉沿active_hero_visual_task及角色来源，世界观沿world_lore_next_action及适用收束；字段随原入口演进，不强制另建同名schema。不能让一个“最新收束”覆盖所有任务，也不能让单个active字段抹掉并行英雄任务。多项任务确需并存时，由该线在其既有状态中保存稳定任务标识和分别的当前指针，旧入口兼容引用保留。同目录多任务只增量更新自己负责的内容；跨任务归并先按下节移交，接收方只写自己的回执。共享规程/公告读main，设计来源读独立分支；不整树覆盖，阅读、采用、执行、用户认可分别记录。

## 同一项目内的任务拆分、并行与归并

本节是可复用的说明制作和接续流程；复用原状态、任务、回传和授权，不新建平行调度系统。不要求一任务一项目，也不要求一个对话只做一个模块。对话数量由当前任务和实际负担决定；用户要求的并行对话由用户打开，助手不能把文档配置写成已自动创建/唤醒对话或子代理。

### 制作项目说明

1. **先固定长期范围。**写清项目目标、角色、事实源入口、分支、授权与保护项。例如“英雄视觉与页面UI”，而非“永远只有两个对话”或“只负责目前这三名英雄”。专属单英雄试点等已有明确范围限制仍有效，不能用弹性分工绕过。
2. **把动态内容留在原状态。**当前有哪些任务、谁负责、是否施工/待接续/暂停/完成/已转交、来源和下一步随工作更新。任务用稳定对象/任务名识别，不用“第一个聊天”作唯一身份；已有编号和字段能承载就复用，只补确需的映射。
3. **成文时统一启动、保存和变更规则。**同一前端项目采用一份完整一致的说明，明确本节和原固定入口；AI整理最终可复制正文，用户不必自行拼接多份不同身份文字。
4. **核实际用途。**检查说明在一对话多任务、多对话并行、减少对话和换人接续时是否仍成立。项目说明发布、前端安装、任务分工实际变更和接续效果分别核实；数量变化通常只更新状态，只有项目职责、权限、入口或长期规则变化才改说明。

### 最低充分任务记录

在原CURRENT_STATE/TASK/RETURN或其现有任务来源中表达以下内容即可，不强制每个任务新建文件、同名字段或另一套台账：

| 内容 | 用途 |
|---|---|
| 稳定任务名/对象及目标 | 区分H01与H02等任务，保留整项任务所需的跨模块上下文 |
| 当前负责范围与执行者/接续状态 | 同一任务谁可写、是否已停止旧执行、能否接任；不用不可取得的会话ID冒充身份 |
| 权威来源、成果版本和已确认边界 | 能读到实际正文、原图/代码及授权，候选不变批准 |
| 已做、未做、依赖和下一步 | 每项任务独立恢复；减少对话不删除未完义务 |
| 转交去向及真实接收记录（仅转交时） | “准备交出”“可接收”“已接收并接管”有证据地区分 |

项目/任务的事实来源不因承接对话变化而迁移或复制。读取相关模块不等于取得全部模块维护权限。一个对话可负责多个任务；同一可修改对象同一时段只设一个有效写入责任方。其他对话可在授权内只读复核或处理不重叠范围；共享文件优先由既有协调责任方归并，独立字段更新也必须核最新版本和冲突。

### 变更分工的实际流程

**一变多：**按可独立交付的对象或阶段拆任务，先保存共同基线及各自边界、依赖、回传位置。新对话实际读取并确认承接范围后再施工；原对话只继续保留给自己的任务或协调工作，不与新对话重复写同一对象。协调可以由现有对话兼任，不强制为N项任务额外开第N+1个对话；这也不授予《乐子象棋》主线身份。

**多变少：**先区分减少原因。任务已完成则保留真实结果；暂缓则保留恢复条件；工作只是转给另一个对话则保留原任务身份和未完成部分，不能记成完成或删除。剩下的一个对话可以同时承担多项任务，不必把多项任务改成一个任务。

**移交/归并的顺序：**原执行者保存实际正文、版本、确认、未验项和未发布成果，发布并读回后明确停止被转交范围的新写入；将该范围标为待接收并保留原责任及去向。接收者核最新HEAD、有效授权、源材料及冲突，实际接收后记录自己承担的范围、来源和逐项下一步。接收未完成时保持待接收，不替对方写成功；原执行者若此后有新材料，另作增量交付，不与接收者双写。同一对话保留部分任务时，只停止转出的部分。原对话不可访问时，按既有接任规则保护可恢复材料并说明缺口，不凭对话沉默、时间经过或文件较新认定其已释放。

**二变一：**可以把两条路线的工作交由一个对话负责，两个原任务/确认链仍保留。若用户同时要求合并目标，先核目标、冲突及授权，再更新任务关系；对话数量减少本身不合并审批、英雄设定或事实源。这里的“归并”是职责与成果接续，不声明平台聊天历史已经合成一个聊天。

**已有对话和新对话：**已有对话按自身明确任务继续；新对话只在明确的当前接续指向及有效接任条件下采用“继续”。三英雄并行时可用“继续H02”；归并后也可用“接续英雄设计汇总”。任务指向冲突时只问最小区分，不要求用户复制长交接。只剩一个未完任务也不得抢占仍在施工的对话。

### 例子和验证边界

- 一个对话做H01/H02/H03：三个任务，一个执行者；需要并行时可改为三个对话各自负责一个。
- 三个对话改两个：可由对话A接续H01/H02、对话B接续H03；H02不因少开一个对话而消失。
- 英雄视觉与页面UI改由一个对话推进：保留两项任务的来源和独立下一步，按当前目标安排顺序；世界观暂停、图稿审批和其他边界不变。
- 旧对话只收束自己负责的一项：其他任务及对话继续；整个项目没有因此完成或暂停。

上述为方法示例，不是已发生的任务变更。先做与文字差分相称的来源、指针、任务遗漏和写入边界核对，再在下一次实际拆分/归并及自然换对话中观察执行；文档核对不能替代前端、并发运行或接续效果。无实际任务变化不制造认领、接收回执或循环检查。

## 增量发布

1. 读取远端HEAD、CURRENT_HANDOFF和本线CURRENT_STATE；需要时读取目标文件、树和差分。接续按当前入口，不从文件名/搜索摘要推断状态。
2. 只修改固定工作目录中的本轮差分。新增候选放candidates/<任务>/<版本>；新素材进入assets/ui，以SHA-256标识。相同字节直接复用已存在Git blob，既有图片和字体不再读出、编码、重新上传。
3. 对文件内容、路径、依赖和审批状态作与改动相称的核对；检查范围和重用证据按UI_WORK_AGREEMENT执行。没有变化就不制造新副本或累计包。
4. 用create_tree复用原Git对象并加入必要新文本/新资产，create_commit生成单次范围明确的提交。update_ref带已读取的expected_sha，force=false；远端变化则先重读和合并，不覆盖另一线。
5. 逐项保存成功上传记录及最终提交。提交后实际读取入口，核对远程树中变更路径/字节和资产身份。发生中断，从有凭据的断点续传；没有成功结果不能宣称完成。GitHub连接器能减少无效搬运，但首次上传新二进制仍有传输成本。
6. 阶段完成、共享阻断或用户收束时交回基准提交、当前状态、批准依据、变更、来源、验证与下一步；旧资产用引用，不每轮携带完整历史。发布与接收/采用分开。
